Lumen — time-series store for edge devices

Lumen ingests metrics from constrained devices and keeps them queryable for 13 months. This documentation site is ordinary static HTML. The assistant in the corner is not: it runs a language model in this tab, on this GPU, with no inference server anywhere.

Quickstart

Install the SDK and point it at a project. There is no server to deploy.

npm i @lumen/sdk
lumen init --project my-project
lumen push --config lumen.config.ts

lumen init writes a project manifest, generates a write key scoped to that project, and creates the ingest endpoint. Keys are shown once and stored in ~/.config/lumen/credentials.json.

Write API

Send one JSON object per measurement. Batches are newline-delimited JSON, capped at 1000 records.

curl https://ingest.lumen.dev/v2/write \
  -H "Authorization: Bearer $LUMEN_KEY" \
  -H "Content-Type: application/x-ndjson" \
  --data-binary @metrics.ndjson

A 200 means the batch was durably queued, not that every point parsed. Per-record rejections arrive in the /v2/ingest-report response and in the project log.

Rate limits

Limits are per project, per minute, and burst is limit × 1.5. Exceeding either returns 429 with a Retry-After header. Free projects are capped at 1,000 writes and 30 days of retention; paid projects raise both on request.

Billing

Usage is billed per million points ingested, monthly, in arrears. There is no egress charge and no charge for queries. Invoices are issued on the first of the month and cover the previous calendar month. Deleting a project removes its points immediately; the invoice is not adjusted.

Troubleshooting

Writes return 202 but no data appears. Query the same window with ?consistency=strong; the default is eventual and can lag a few seconds.

Device clocks drift. Lumen rejects points more than 24 hours in the past. Send X-Lumen-Offset-Ms to correct for a known device offset.

    Put this on your own site

    Five lines. Point dataDir at your content folder and the pipeline crawls it.

    npx wasmtune dataset && npx wasmtune train && npx wasmtune eval && npx wasmtune convert
    <script type="module">
  import { mountAssistant } from "wasmtune/chat";
  await mountAssistant({ target: "#chat", siteName: "Lumen" });
</script>

    The first visitor downloads the weights once and the browser caches them; every later visit is offline. This page calls exactly the two lines above — the panel above is a few more wasmtune/chat exports (detectHardware, fitReport, pickModel) used for display.

    wasmtune vs. a RAG / vector-DB setup

    Both answer from your content. Only one of them needs a running server to do it.

    wasmtunehosted RAG / vector DB
    Inference runsin the visitor's tab, over WebGPUon your GPU box or vendor's cluster
    Server bill$0 — weights are static files on a CDNper query, forever, plus a always-on indexer
    Needs a backendno. any static host: Pages, Netlify, S3yes: a running service with uptime and scaling
    Network at answer timezero — works in airplane modeone round trip per question, minimum
    User contentnever leaves the deviceshipped to a third party on every question
    Per-visitor tieringautomatic from measured hardwareone server config for everyone
    Fresh contentre-crawl + retrain in CIre-embed and re-index
    Ceiling0.1B–4B models: short, grounded, honest answersunbounded context, citations, arbitrary documents

    Where RAG still wins: your corpus is large or changes hourly, you need verbatim quotes with citations, or answers must span dozens of documents. wasmtune is for the other half of the problem — a small, stable corpus and a question that a 1B model can answer without inventing anything.
